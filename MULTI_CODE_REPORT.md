## 3. Парсинг строки с кодами

Строка из поля `Код производителя` обрабатывается функцией `parseCodeInput`:

1. Деление по разделителю `,`.
2. `trim()` для каждого элемента.
3. Удаление пустых строк.
4. Удаление дублей через `Set`.
5. Добавление в итоговый массив только первого вхождения каждого кода.

Примеры:

- `code1, code2, code3` -> `code1`, `code2`, `code3`
- `code1,code2,code3` -> `code1`, `code2`, `code3`
- `code1,   code2,    code3` -> `code1`, `code2`, `code3`
- `code1,` -> `code1`
- `, code1, , code2` -> `code1`, `code2`

Если после очистки список пустой, popup показывает:

```text
Введите хотя бы один код
```

## 4. Пустые значения и дубликаты

Пустые элементы удаляются после `trim()`, поэтому `A,, B, , C,` превращается в `A`, `B`, `C`.

Дубликаты удаляются без сортировки. `A, B, A, C, B` превращается в `A`, `B`, `C`, потому что первые вхождения сохраняются в исходном порядке.

## 5. Лимит 20 кодов

Добавлена константа:

```js
const MAX_CODES_PER_SEARCH = 20;
```

Лимит выбран по требованию итерации. Он защищает popup и 1С от слишком большого пользовательского ввода за один запуск. Если после очистки больше 20 кодов, запросы не отправляются и показывается ошибка:

```text
Слишком много кодов за один поиск. Максимум: 20.
```

## 6. Лимит параллельности 2

Добавлена константа:

```js
const MAX_PARALLEL_REQUESTS = 2;
```

Лимит выбран по требованию итерации. Он снижает пиковую нагрузку на HTTP-сервис 1С: даже если пользователь ввёл 20 кодов, один popup держит не больше двух активных запросов одновременно.

## 7. Очередь запросов

`runWithConcurrencyLimit` принимает массив элементов, лимит и async worker. Алгоритм:

1. Создаётся массив результатов той же длины.
2. Запускаются первые элементы до лимита параллельности.
3. После завершения любого worker освобождается слот.
4. В свободный слот запускается следующий элемент.
5. Результат каждого worker записывается по исходному индексу.
6. Callback `onItemSettled` обновляет прогресс `Обработано X из N`.

Итоговый массив возвращается в порядке исходных кодов, даже если HTTP-ответы пришли в другом порядке.

## 8. Ошибка одного кода

`fetchPriceHistoryForCode` не бросает ошибку наружу для обычных проблем одного кода. Вместо этого возвращается объект:

```js
{
  code: "ABC-1000",
  ok: false,
  status: 404,
  error: "Код не найден",
  rawText: "..."
}
```

Ошибки HTTP, невалидный JSON при HTTP 200, network/fetch error обрабатываются как ошибка конкретного кода. Остальные коды продолжают выполняться.

## 9. Отображение нескольких результатов

Для нескольких кодов popup показывает:

- общий блок `Результаты поиска`;
- количество кодов;
- количество успешных результатов;
- количество ошибок;
- прогресс `Обработано X из N` во время выполнения;
- отдельную карточку `Код: ...` для каждого кода.

Успешная карточка использует существующий красивый рендер price-history: последняя цена, средняя цена, список цен, поставки, рекламации, SAP-коды и дополнительные данные.

Ошибочная карточка показывает человекочитаемое сообщение и HTTP-статус, если он есть. Сырой технический ответ отображается только внутри `<details>`.

## 12. Ручная проверка

Проверено по коду и через VM-тесты:

- одиночный режим продолжает использовать существующий `renderResult`;

## 13. Остаточные риски

- При 20 кодах popup выполнит до 20 HTTP-запросов, но только по 2 одновременно. Это снижает пиковую нагрузку, однако суммарная нагрузка на 1С всё равно возрастает по сравнению с одним кодом.
- Если один ответ 1С очень долгий, очередь будет ждать освобождения слота; popup остаётся в состоянии выполнения до завершения всех запросов.
- Timeout явно не добавлялся, чтобы не менять сетевое поведение существующего расширения. Если браузер или сеть завершат fetch ошибкой, она будет показана только для конкретного кода.
- Реальную совместимость с 1С нужно проверить в Chrome на машине с доступом к сервису.
